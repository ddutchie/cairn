# v2.5.7

## Added

- **Custom HTTP services can now authenticate with OAuth.** Previously a custom HTTP service (any REST endpoint exposed to the AI as a tool) could only send a static API key or bearer token via a header — fine for key-based APIs, but useless for services whose access tokens expire (Gmail, Microsoft Graph, and most modern OAuth 2.1 APIs), where you'd have to paste a fresh token roughly every hour. A service can now be set to **OAuth**: you sign in once in the browser (the same PKCE + dynamic-client-registration flow Cairn already uses for OAuth MCP servers), and Cairn stores the tokens encrypted in your OS keychain, refreshes them automatically as they expire, and injects `Authorization: Bearer <token>` on every request. Nothing is written to the database and no token is ever exposed to the model. This is the foundation for a wave of new one-click community connectors that talk directly to a vendor's REST API without needing a gateway. Key-based and header-secret services keep working exactly as before.
- **The community registry can ship OAuth service presets.** Registry `service` entries gained optional `authMode` and `oauth` fields, so a connector can declare "this REST service uses OAuth" (with an optional pre-set scope / discovery base / client id). For any authorization server that supports dynamic client registration — most modern ones — no per-vendor setup is needed: install, click Connect, done.
- **Connect a custom OAuth service from Settings.** The Add/Edit service form now has an **Authentication** toggle (Headers / API key ↔ OAuth), matching the MCP server form. Choose OAuth and you can optionally set a scope and authorization-server URL (leave the latter blank to auto-discover from the API URL). Once saved, the service row shows a **Sign in / Connected / Sign out** control — the same browser flow, cancel button, and error handling as OAuth MCP servers. Installing an OAuth service from Browse Community works the same way: it installs disabled with an "OAuth" badge, then you click Connect.

## Changed

- **Tool calls to MCP servers and HTTP services now show a clickable result chip.** When the chat assistant calls an external tool (a Confluence search, a web search, a Jira lookup, a GitHub query…), the result used to be an opaque "✓ Tool" chip. Cairn now pulls the most useful link out of the tool's response and shows it as a chip you can click to open in your browser — the Confluence page, the search hit, the pull request, and so on. It works across most services automatically (no per-connector configuration) by recognising the common shapes REST APIs use for links and titles, and it only ever opens `http(s)` links. Native note/task tool calls keep their existing in-app chips.


## Fixed

- **Note writes no longer fail when the model emits slightly-off JSON.** When the AI called a note tool like `ensure_note`/`patch_note`/`append_to_note` and its `content` contained markdown (multi-line bodies, code blocks, quotes), some models produced *nearly*-valid tool-argument JSON — most commonly a real newline typed straight into a string instead of an escaped `\n`, which the strict parser rejected. The call would fail and the model would often loop on the same mistake. Cairn now parses tool-call arguments with a strict-first, repair-fallback strategy: it still tries a clean parse first, and on failure it applies only *provably lossless* structural repairs — escaping raw control characters inside a string and removing trailing commas — before retrying. Crucially, note content always round-trips byte-for-byte: repairs that could alter what a note actually says (stripping a wrapping code fence, rewriting curly quotes) are deliberately *not* performed, so content containing code fences or smart quotes is preserved exactly. Genuinely broken JSON still surfaces a clear error to the model rather than silently running with empty arguments or guessing at content. Applied consistently across the chat loop, the agent loop, the subagent dispatcher, and the tool builder.
- **`ensure_note` fails loud on truncated calls instead of silently doing nothing.** If a tool call arrived with a missing/garbled `projectId` or `title` (e.g. a payload that got truncated mid-stream), `ensure_note` now returns a structured, machine-readable error (`{ error: "missing_required_field", field, received_keys }`) so the AI knows exactly what to re-send — previously a half-formed call could look like it succeeded or fail with an unhelpful message. A non-string `content` is likewise rejected with a clear reason.
- **`ensure_note` guards against accidentally clobbering a large note.** A truncated payload could land as a tiny `content` string (say `"wip"`) on a title that already holds a large document and silently overwrite it. `ensure_note` now refuses an update that would drastically shrink a substantial existing note (new content under 20% of the old length, when the old note was ≥200 characters) and returns a `possible_accidental_overwrite` error suggesting `append_to_note`/`patch_note` instead. If the shrink is genuinely intended, pass the new `overwrite: true` argument. Routine edits, condensing, and clearing small notes are unaffected.
