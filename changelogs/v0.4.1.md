# v0.4.1 — Order of Concerns Sprint

Continuation of the v0.4.0 compartmentalising work. This release is entirely internal — no new user-facing features. Focus: correctness bugs, error surfacing, duplication elimination, and structural hygiene throughout the data layer and renderer store.

---

## Bug Fixes

### IPC error handling was completely missing (critical)

Every `ipcMain.handle` in `handlers.ts` and `registerAppHandlers` was unwrapped — any SQLite error, file I/O failure, or missing argument would propagate as an unhandled rejection, silently swallowed by the renderer's fire-and-forget `ipc()` helper. Users had no way of knowing writes failed.

- All handlers now wrapped in `try/catch` via a `handle()` helper
- Every handler returns `{ data: T } | { error: string }` consistently
- The `ipc()` and `ipcAwait()` store helpers now detect `{ error }` responses and dispatch a `cairn:ipc-error` CustomEvent
- `page.tsx` listens for `cairn:ipc-error` and shows an auto-dismissing toast (bottom-right, 5s) so write failures are always visible to the user

### Nullable COALESCE update bug (data correctness)

`COALESCE(?, existing_col)` cannot set a column back to `NULL` — passing `null` just keeps the existing value. This silently broke `restoreCard`, `restoreNote`, and any future clear-field operation.

- Added `restoreCard(db, id)`, `restoreNote(db, id)`, and `clearCardDueDate(db, id)` to `queries.ts` — each uses an explicit `SET col = NULL` statement
- `db:card:update` and `db:note:update` handlers now detect `archivedAt: null` and `dueDate: null` in the patch and route to the dedicated helpers instead of `updateCard`/`updateNote`

### `updateTag` returned a raw SQLite row

`queries.ts:updateTag` was the only query helper that didn't pipe its result through the `toTag()` mapper — it returned the raw `better-sqlite3` row object to the store. Fixed; now consistent with all other query helpers.

### Dashboard bootstrap script injection

`buildBootstrap(projectId, workspaceId)` in `dashboard-view.tsx` injected IDs directly into a raw JavaScript string using single-quote delimiters. An ID containing a single quote (unlikely but not impossible for externally-modified DBs) would break the injected script. All ID injections now use `JSON.stringify()`.

## Architecture

### `electron/shared/text-utils.ts` — shared pure helpers

`toSlug` and `stripMarkdown` had no native dependencies but were duplicated between `electron/notes-files.ts` and `electron/mcp-server.ts` (the ABI isolation constraint only applies to the `better-sqlite3` binding, not pure JS). Extracted to `electron/shared/text-utils.ts`. Both files now import from the shared module.

### `src/store/ipc.ts` — single IPC helper module

`isElectron()`, `ipc()`, and `ipcAwait()` were copy-pasted verbatim into five slice files (`workspace.ts`, `board.ts`, `notes.ts`, `tags.ts`, `chat.ts`). Extracted to `src/store/ipc.ts`. All five copies removed.

### `queries.ts` — missing lookup helpers

`getProjectById`, `getNoteById`, `getCardById`, and `generateId` added. Two handlers (`db:project:delete`, `db:note:delete`) were doing raw `db.prepare("SELECT ... WHERE id = ?").get(id)` inline instead of calling query helpers. Both now use the typed helpers.

### Atomic project creation (N+1 → 1 IPC call)

`workspace.ts:createProject` previously fired 6 sequential IPC calls (1 project + 5 columns). A partial failure would leave the DB and store diverged with no error surface. The `db:project:create` handler now creates the project and all 5 default columns in a single atomic call, returning `{ project, columns }`. The renderer slice consumes the authoritative columns from the server response.

`handlers.ts` now imports `DEFAULT_COLUMNS` from `electron/db/defaults.ts` — eliminating the inline copy that was the third duplication of that data.

### `DEFAULT_COLUMNS` consolidated

Previously defined in three places: `src/lib/constants.ts` (renderer), `electron/db/defaults.ts` (electron), and hardcoded inline in `workspace.ts`. The renderer-side `src/lib/constants.ts` and the electron-side `electron/db/defaults.ts` remain as two bundle-boundary copies of identical data (the renderer cannot import from `electron/`). The inline `workspace.ts` copy is gone.

### Constants consolidated

- `PRIORITY_COLORS` (Tailwind classes) moved from `src/lib/utils.ts` into `src/lib/constants.ts` alongside `PRIORITY_CSS_COLORS`. Re-exported from `utils.ts` for backwards compatibility — all existing imports continue to work.
- `AI_CONFIG_KEY` and `ACTIVE_PROJECT_KEY` were each defined twice (`src/store/slices/ui.ts` and `src/store/index.ts`). Both moved to `src/lib/constants.ts` and imported everywhere.

### Versioned migration runner

Replaced the `PRAGMA table_info(notes)` / `ALTER TABLE` approach with a proper versioned migration runner using `PRAGMA user_version`:

- Each migration is a numbered function in a `MIGRATIONS` array
- `PRAGMA user_version` tracks which migrations have been applied
- Runs inside a transaction — migrations are atomic
- `PRAGMA foreign_keys = ON` now set explicitly before `db.exec(SCHEMA_SQL)` in `applySchema` (previously relied on the `PRAGMA` inside the schema SQL string, which ran after the connection opened)
- Rules: never edit existing migrations, only append

**Migration v1** — `notes.type` column (converts the old ad-hoc check)  
**Migration v2** — 6 missing performance indexes:

| Index | Query it serves |
|-------|----------------|
| `notes(updated_at)` | Default note list sort |
| `notes(archived_at)` | All note queries filter `WHERE archived_at IS NULL` |
| `task_cards(updated_at)` | Recent activity sort |
| `task_cards(archived_at)` | All card queries filter `WHERE archived_at IS NULL` |
| `mcp_notifications(read)` | Polled every 1 second in main process |
| `chat_messages(thread_id)` | FK column — SQLite does not auto-index FKs |

### MCP server — foreign key enforcement

The MCP server opened the DB without calling `applySchema`, so `PRAGMA foreign_keys = ON` was never set for MCP connections. All MCP writes now run without referential integrity enforcement. Fixed: `db.pragma("foreign_keys = ON")` and `db.pragma("journal_mode = WAL")` called immediately after DB open in `mcp-server.ts`.

### Chat executor — tool parity with MCP

Three tools existed in the MCP server but were missing from the in-app AI:

| Tool | Notes |
|------|-------|
| `update_project` | Chat AI can now update project name, description, icon, status, priority, dueDate |
| `delete_project` | Chat AI can now delete a project (with `.md` file cleanup) |
| `list_recent_activity` | Chat AI can now list recent notes and tasks |

All three added to `executeTool`, `TOOLS`, and `TOOL_LABELS`.

### `newId()` uses nanoid

`electron/db/utils.ts:newId()` was using `Math.random().toString(36).slice(2, 14)` — approximately 42 bits of entropy. Replaced with `nanoid(12)` — 71 bits of entropy, same character set used by the renderer's `id()` helper.

## Testing

### Vitest works after `npm run rebuild`

Previously, running `npm run rebuild` (which ends with `@electron/rebuild`) left `node_modules/better-sqlite3` with the Electron ABI binary. Vitest (plain Node) then couldn't load it, causing all 22 DB tests to fail.

Fixed with a two-part solution:

1. **`vitest-native/` directory** — `scripts/rebuild-native.js` now runs `npm rebuild better-sqlite3` (system Node ABI) and saves a copy to `vitest-native/` *before* the Electron rebuild overwrites `node_modules/`.
2. **`vitest-sqlite-shim.cjs`** — aliased as `better-sqlite3` in `vitest.config.ts`. Wraps `Database` to always pass `nativeBinding: vitest-native/better_sqlite3.node`, so the correct ABI is used regardless of what's in `node_modules/`.

All 51 tests pass after a full `npm run rebuild`.
