## What's new

### Changed

- **A shorter, friendlier first-run setup.** Onboarding dropped from nine screens to five: choose folder → workspace → appearance → AI → land in the app. The MCP-config, embeddings, and view-visibility screens are gone from the required flow — none of them blocks getting started, and all three still live in Settings (Tools/MCP, Embeddings, and General → View visibility) exactly as before. The progress dots now reflect the real path instead of overstating how much is left.
- **Appearance setup now includes accent colour and note font.** The appearance step already let you pick a theme and text size; it now also has the accent-colour swatches and the Sans / Serif / Mono note-font picker (with a live preview rendered in the chosen font), so the whole look of the app is set in one place up front. All of it remains editable in Settings → General.

### Fixed

- **A brand-new workspace's chat now works immediately, without restarting the app.** On a fresh install Cairn boots before a workspace folder exists, so it opens a temporary empty database; the onboarding wizard then swaps in the real workspace database in place. Chat, the coding agent, MCP servers/custom services, the tool builder, git tools, and LLM usage recording were all bound to that temporary database at startup and never re-bound — so for the whole first session the AI saw an empty workspace, every write ("create a note", "add a card") failed with "Project not found", and anything it did manage to write landed in a hidden folder that the app never showed. Restarting the app fixed it, which is why it looked like "chat isn't connected to my workspace yet". All of these now resolve the current workspace at the moment they're used, so the handover during onboarding is seamless.
- **Changing your workspace folder no longer half-switches the app.** The same fix applies to Settings → General → change folder: chat, the agent, git, tools, and usage tracking previously kept reading and writing the *old* workspace (including writing note files back into it) until the app was fully quit and relaunched.
- **Chat conversations now load when the workspace changes.** Threads and messages are stored per workspace, but were only ever read from the database on a cold start — so finishing onboarding or switching workspace folders left the chat list showing the previous workspace's (or no) conversations until restart.
- **Cairn notices external MCP writes again after a workspace change.** The background watcher that detects writes made by the MCP server (and drives the notification badge + live refresh) stayed pointed at the previous workspace's database file, so MCP activity in the new workspace went unnoticed for the rest of the session.
- **The MCP server now follows the app when you change workspace folder.** A running `cairn-mcp` process resolved its database once at startup and never re-checked, so after the app switched workspace folders the server kept reading — and writing note files into — the *old* workspace until it was restarted. It now re-resolves the active workspace (throttled) and reopens the connection when it changes. You can also pin it explicitly with `CAIRN_DB_PATH=/path/to/workspace` (or a `cairn.db` file), and `get_cairn_context` now reports the resolved `runtime.dbPath` / `runtime.workspacePath` so drift is diagnosable at a glance.
- **The knowledge graph stays correct after MCP edits.** Notes and cards created or edited through the MCP server didn't refresh the derived relationship cache, so `get_knowledge_graph` / `get_neighbors` kept serving co-mention/keyword/assignee/wikilink edges from the workspace's previous state (a staleness that persisted even across an MCP restart). MCP write tools now invalidate and recompute those edges, matching the in-app write path.
- **Clearer MCP startup diagnostics.** When no workspace can be found the server now points you at both fixes (open the app, or set `CAIRN_DB_PATH`) instead of a bare "open the Cairn app first", and it warns on stderr when it's pointed at a database with no Cairn schema yet (the MCP server never runs migrations — the app owns them).
